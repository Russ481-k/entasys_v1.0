## 경영진 요약

### 현황 개요
현재 운영 중인 Entasys v1.0 로그 처리 시스템에서 **데이터 손실률 20-30%**라는 심각한 문제가 발생하고 있습니다. 시스템 리소스가 충분함에도 불구하고 이러한 데이터 누수가 지속되고 있어, 비즈니스 연속성과 컴플라이언스 요구사항에 대한 위험이 증가하고 있습니다.

## 현 시스템 분석

### 시스템 아키텍처 현황

```
┌─────────────┐    ┌─────────────┐    ┌─────────────┐    ┌─────────────┐    ┌─────────────┐
│  UDP:514    │ -> │  Logstash   │ -> │    Kafka    │ -> │ OpenSearch  │ -> │   Next.js   │
│             │    │  Producer   │    │             │    │             │    │  Dashboard  │
│ Syslog 수신  │    │ Java 8.9.0  │    │ Confluent   │    │   2.13.0    │    │   React     │
│             │    │ 256MB RAM   │    │    7.3.0    │    │ Single Node │    │             │
└─────────────┘    └─────────────┘    └─────────────┘    └─────────────┘    └─────────────┘
```

### 주요 문제점 분석

#### 1. Logstash 구조적 한계
- **JVM 메모리 오버헤드**: 기본 512MB 할당으로 비효율적 리소스 사용
- **가비지 컬렉션 지연**: 고부하 시 수 초간 전체 파이프라인 정지
- **UDP 큐 제한**: 50,000개 초과 시 패킷 무조건 폐기
- **Ruby 필터 성능**: 문자열 처리 시 CPU 100% 사용률 도달

**성능 병목 코드 예시**:
```ruby
ruby {
  code => '
    # 매 로그마다 실행되는 고비용 연산
    index_domain = original_domain.downcase
                                 .gsub(/\./, "-")
                                 .gsub(/[^a-z0-9\-]/, "_")
  '
}
```

#### 2. OpenSearch 비효율성
- **실시간 인덱싱 오버헤드**: 일일 신규 인덱스 생성으로 메타데이터 급증
- **전체 필드 인덱싱**: 모든 컬럼을 검색 가능하게 설정하여 저장공간 10배 낭비
- **단일 노드 구성**: I/O 병목으로 인한 쓰기 성능 제약
- **집계 쿼리 지연**: 복합 조건 검색 시 30초 이상 응답 시간

#### 3. 네트워크 프로토콜 한계
- **UDP 패킷 손실**: 네트워크 혼잡 시 재전송 메커니즘 부재
- **백프레셔 미구현**: 하위 시스템 과부하 시 상위 시스템 제어 불가
- **동기식 처리**: 단일 지점 장애가 전체 파이프라인에 영향

### 비즈니스 영향도
- **컴플라이언스 리스크**: 로그 보존 의무 위반 가능성
- **보안 위협 탐지 지연**: 실시간 위협 분석 불가
- **운영 효율성 저하**: 시스템 장애 원인 분석 어려움
- **고객 서비스 품질**: 성능 이슈 사전 감지 한계

## 제안 아키텍처

### 목표 아키텍처: Cloud-Native 로그 처리 플랫폼

```
┌─────────────┐    ┌─────────────┐    ┌─────────────┐    ┌─────────────┐    ┌─────────────┐
│ Syslog TCP  │ -> │ Fluent Bit  │ -> │    Kafka    │ -> │ ClickHouse  │ -> │   Grafana   │
│             │    │             │    │             │    │             │    │             │
│ 514 포트    │    │ CNCF 검증   │    │ 분산 처리   │    │ 컬럼형 DB   │    │ 실시간 UI   │
│ 신뢰성 보장  │    │ 50MB RAM   │    │ 파티셔닝    │    │ 90% 압축   │    │ WebSocket   │
└─────────────┘    └─────────────┘    └─────────────┘    └─────────────┘    └─────────────┘
```

### 핵심 기술 구성요소

#### 1. Fluent Bit (로그 수집기)
**선택 근거**:
- **CNCF 인큐베이팅 프로젝트**: 글로벌 표준 준수
- **경량 아키텍처**: 50MB 메모리로 고성능 구현
- **네이티브 백프레셔**: 다운스트림 과부하 시 자동 제어
- **플러그인 생태계**: 200+ 커넥터 지원

**주요 기능**:
- TCP/UDP 듀얼 프로토콜 지원
- Lua 스크립트 기반 고속 파싱
- 메모리 기반 버퍼링 (100MB)
- 배치 처리 최적화

#### 2. ClickHouse (분석형 데이터베이스)
**선택 근거**:
- **컬럼형 스토리지**: 분석 쿼리 최적화
- **압축률 90%**: 동일 데이터 1/10 크기로 저장
- **선형 확장성**: 노드 추가로 성능 비례 증가
- **SQL 호환성**: 기존 쿼리 로직 재사용 가능

**성능 특징**:
- 100억 로그에서 1초 내 집계
- 실시간 데이터 입력과 동시 쿼리
- 자동 파티셔닝 및 인덱싱
- 분산 조인 연산 최적화

#### 3. Grafana (모니터링 대시보드)
**선택 근거**:
- **실시간 스트리밍**: WebSocket 기반 즉시 업데이트
- **다양한 시각화**: 100+ 패널 타입 지원
- **알림 시스템**: 임계치 기반 자동 경보
- **멀티 데이터소스**: ClickHouse, Kafka, Prometheus 통합

### 기술 스택 상세 설계

#### Fluent Bit 설정 최적화
```ini
[SERVICE]
    Flush         1              # 실시간 처리를 위한 1초 플러시
    Grace         30             # 우아한 종료 대기시간
    HTTP_Server   On             # 메트릭 수집 활성화
    storage.path  /opt/fluent-bit-storage
    storage.backlog.mem_limit 100M  # 메모리 기반 백로그

[INPUT]
    Name              syslog
    Mode              tcp        # UDP 대신 TCP로 신뢰성 확보
    Listen            0.0.0.0
    Port              514
    Buffer_Chunk_Size 1M         # 대용량 청크로 효율성 향상
    Buffer_Max_Size   10M

[FILTER]
    Name    lua
    Match   palo.*
    Script  /opt/scripts/palo-parser.lua
    Call    parse_palo_alto_log

[OUTPUT]
    Name        kafka
    Match       *
    Brokers     kafka-cluster:9092
    Topics      palo_logs_v2
    Compression gzip
    Batch_Size  1000
    Workers     4                # 멀티 워커 병렬 처리
```

#### ClickHouse 스키마 설계
```sql
CREATE TABLE palo_logs_realtime (
    timestamp DateTime64(3, 'Asia/Seoul') CODEC(Delta, ZSTD),
    domain LowCardinality(String),     -- 메모리 90% 절약
    log_type LowCardinality(String),   -- 카디널리티 최적화
    source_ip IPv4 CODEC(ZSTD),        -- IP 전용 타입
    dest_ip IPv4 CODEC(ZSTD),
    bytes UInt64 CODEC(Delta, ZSTD),   -- Delta 압축
    action LowCardinality(String)
) 
ENGINE = MergeTree()
PARTITION BY toYYYYMM(timestamp)       -- 월별 파티션
ORDER BY (timestamp, domain, source_ip)
SETTINGS 
    index_granularity = 8192,          -- 인덱스 최적화
    compress_marks = true,
    compress_primary_key = true;
```

**장점:**
- 기존 팀의 운영 경험 보유
- 성숙한 문서화 및 커뮤니티

**장점:**
- 무손실 데이터 처리 (99.9% 보장)

- 초기 학습 비용 ($3,000)

- 새로운 운영 프로세스 구축

**장점:**
- 최고 수준의 메모리 안전성
- 우수한 단일 머신 성능

**단점:**
- 상대적으로 새로운 기술
- 제한된 플러그인 생태계
